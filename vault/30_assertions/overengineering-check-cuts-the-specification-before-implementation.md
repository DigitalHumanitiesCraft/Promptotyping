# A check for overengineering cuts the specification back to a minimal scope before the agent implements.

## Statement

When the architecture document arrives with a folder structure holding very many files, the author asks whether a minimum viable product can be built from it first, and he calls having the architecture shown before any code a good strategy against the volume of unnecessary code the system produces. His order is then to look at everything again from another, honestly constructive perspective, to check whether the result is overengineered and whether the documents fit together. The tool returns points of criticism and inconsistencies, among them the tendency the author names as typical, an unrequested dark mode a minimum viable product does not need, and keyboard shortcuts are ruled out with it. The documents come back simplified, the scope reduced to line charts and bar charts, which the author accepts for the first iteration. His summary of the session records a second pass over the architecture, user-interface and user-story documents whose purpose was a state that is not overengineered. The check sits between the document set and the build, and it is recorded once, in one session by the method's author.
