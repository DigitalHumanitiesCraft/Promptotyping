# Distillate: Promptotyping live demonstration, video 2

The second recording from January 2026 runs a full session with an agentic coding tool, from a folder of Austrian knowledge-balance spreadsheets to a working dashboard. It is the operational counterpart to video 1 and carries the working steps at prompt level, among them the milestone cut, the overengineering check, the screenshot and console back channel, and the journal that stands in for a commit.

## Core statements

- The Preparation phase of the demonstration consists solely of gathering the Excel documents of the knowledge balance, after which the Exploration phase has the agentic tool explore the data and carry that knowledge into a `data.md`. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-setup]] ^s1
- The prompts are dictated by speech to text, and the recording is paused during the longer runs of the tool rather than filmed throughout. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-dictation]] ^s2
- The tool uses several commands to find the documents and identifies 76 Excel documents in the data folder, after which the speaker grants the rights to edit the files and extends the task. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-76-files]] ^s3
- With very many Excel files the tool is told to create Python scripts for the exploration and to document those scripts, which improves the overview; the speaker notes that the speech recognition garbled this addendum and considers it understandable enough. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-scripts-rationale]] ^s4
- The exploration step yields three Python scripts, a `scripts.md` summarising how the data were explored, three JSON documents holding the extracted data, and the `data.md`. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-exploration-result]] ^s5
- The `scripts.md` documents what lies in the scripts folder and is thereby itself a Promptotyping Document that stays where it is, while the `data.md` moves into a knowledge folder, and the move is reported back to the tool because it otherwise works from an outdated picture of the file tree. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-file-move]] ^s6
- The speaker names a second exploration from another perspective, run in a fresh session as a check, as the sensible step at this point, which yields two variants of `data.md` that can be merged; the result of the first round is neither perfect nor complete and the demonstration proceeds anyway. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-second-pass]] ^s7
- A prepared prompt defines the target application roughly as a static web page with HTML and CSS following the paradigm "Overview first, filter, and details on demand", Shneiderman's Information Seeking Mantra, which already puts context into play. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-target-definition]] ^s8
- The speaker states that this specification can be expanded considerably by supplying Markdown documents of one's own, a `design.md`, a `user-interface.md` or a `research.md`, and by placing the questions of HTML, CSS, JavaScript and the remaining architecture into an `architecture.md`, which can be worked out more cleanly in separate steps. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-doc-expansion]] ^s9
- Three documents are created in one go and the tool is tasked with exploration again, under the guiding question of how data points, information and knowledge entities have to be connected before being distilled into the Markdown documents; how much time is invested at this point is free, and knowledge from a publication or another interface could be brought in for the interface design. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-three-docs]] ^s10
- The resulting `architecture.md` describes a static single page application following the Visual Information Seeking Mantra, which the speaker had not stated and which was clear to the system from the given context, together with HTML5, CSS, responsive design, vanilla JavaScript without a build step, D3.js as the only library allowed, and JSON and CSV as data formats. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-architecture-result]] ^s11
- The proposed folder structure holds very many files, and the speaker calls it a good strategy to have the architecture shown first, to escape the problem that the system produces a great deal of code that is not all necessary, and asks whether a minimum viable product can be built from it first. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-mvp-check]] ^s12
- The order is to look at everything again from another, honestly constructive perspective and to check whether the result is overengineered and whether the documents fit together; the instruction to be honest strikes the speaker as odd and works well in his experience. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-honesty-prompt]] ^s13
- A matrix is a form of juxtaposition, and the Thinking Matrix means using that juxtaposition of all the Markdown documents as a thinking tool. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-thinking-matrix]] ^s14
- The tool returns points of criticism with several recommendations and identifies inconsistencies, which the speaker values because those are better cleared up beforehand; he names the typical tendency of LLMs to add an unrequested dark mode that a minimum viable product does not need, and rules out keyboard shortcuts as well. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-inconsistencies]] ^s15
- Accessibility is likewise ruled out at this point as something to be done later. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-accessibility-deferred]] ^s16
- The intent behind the implementation plan is to give the LLM concrete milestones that can be checked independently, and the speaker holds that this would probably happen by itself while a more precise specification is better, and that one could work far more strongly into the plan with concrete requirements for how the milestones are to be tested. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-milestones]] ^s17
- The documents come back simplified with a summary of the changes, the scope reduced to line charts and bar charts, which the speaker calls entirely acceptable for Promptotyping iteration 1, since the first variation comes first and the knowledge then lying in the folder can be reused. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-scope-reduction]] ^s18
- With a GitHub repository present the speaker would commit at this point, and without a repository the journal takes that place. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-journal-instead-commit]] ^s19
- Thinking about documentation from the start is worthwhile because it keeps the next Promptotyping iteration from repeating certain errors and because other possibility spaces can be exhausted. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-documentation-rationale]] ^s20
- With the context window full the tool performs a context compression by itself, summarising and distilling the content of the window and handing the compressed context to the continuing session. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-compaction]] ^s21
- The resulting `journal.md` records the data analysis with the number of Excel files and their findings, the result stored in `data.md`, the dashboard planning, the critical check and the simplification, which are the steps actually carried out, and the speaker notes how well the LLM works at this meta level. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-journal-content]] ^s22
- Whether a `consistency-matrix.md` and an `implementation-plan.md` are really needed the speaker leaves open and would rather remove them again; for the moment the tool needs that information to carry the distilled knowledge into the Markdown documents, and it would be synthesised back into the other documents later, since the knowledge base is a living document. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-living-docs]] ^s23
- The speaker deliberately triggers the compact function to summarise the whole context window before going into the implementation plan, which consists of eight milestones, and saves the summary of the session so far as a precaution. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-compact-milestones]] ^s24
- For the aggregation step the tool reads `architecture.md` and `data.md` and has the existing analysis scripts and the `scripts.md` as context to look things up in, which is where the documentation pays off for the later working steps of the agents; the better distilled and the more compact the material, the better the LLMs work. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-context-payoff]] ^s25
- The tool at first writes no scripts for going through the very numerous spreadsheets, and the speaker intervenes in the middle of the run. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-intervention]] ^s26
- The exploration phase was evidently not thorough enough, and the explicit order is to update the `data.md` and work the new knowledge back into it; the better the preparation, the better all later steps work. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-exploration-feedback]] ^s27
- When the run stops the speaker names two strategies, `continue` to carry on within the procedure that follows the plan, and having the plan updated instead. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-continue]] ^s28
- The advantage of producing an `index.html` is that the data have to be processed correctly and displayed in the browser, which is an easier way for experts to verify the data than checking the generated aggregates directly. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-interface-verification]] ^s29
- The browser console supplies the feedback of the browser, shows a real error the speaker rates as a small matter, and its information can be played back to the LLM depending on which errors occur. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-console]] ^s30
- The reason for the screenshot back channel is that the system does not see the images and never sees the web page, while it could have access to the console with a live server activated, so the screenshots are new information for the tool. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-screenshots]] ^s31
- At the point where the tool analyses the screenshots the Critical Expert in the Loop would be needed to check whether what is shown is actually right, and therein lies the challenge; what stands in the analysis is hallucinated and could well be right, and the problem remains. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-verification-limit]] ^s32
- A remaining user-interface error at a range element has to be addressed very concretely, and the speaker names the element by its ID because the ID is an identifier for the LLM too, by which the element can be found; passing it with a hash would be cleaner, which presupposes HTML-specific knowledge, and the Expert Developer has to be in the loop as well. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-identifier]] ^s33
- The speaker classes the working mode as no longer vibe coding, notes that much can be done without knowing much about web development while the situation is ambivalent and vibe coding has its limits, holds that the more domain knowledge is present the better it works, and considers it feasible and urgently indicated to train people within one semester to practise informed vibe coding with sufficient AI coding literacy. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-ai-coding-literacy]] ^s34
- Clicking through the interface reveals that the display does not match the selected period and that the filter apparently shows the total sum throughout, and this is how one forms an opinion and iterates with the tool until a workable state is reached. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-click-through]] ^s35
- The speaker classes the closing design experiment in the style of Frank Herbert's Dune as an unprofessional step that shows how radically different things can be tried with such interfaces, possibly yielding interface elements and designs nobody had thought of, which widens the possibility space and lets iteration 1 teach something for the next phase. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-design-experiment]] ^s36
- A single prompt produces an outlandish science-fiction interface the speaker finds impressive, whether the whole thing makes sense he leaves open, and exploring the possibility space is precisely what Promptotyping is about. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-possibility-space]] ^s37
- Orders of this kind can be thrown in mid-run; the tool pauses the running task, goes through all Markdown documents and brings them up to date so that the knowledge worked out lies in those documents, then proposes further actions. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-midrun-commands]] ^s38
- The session needed a second iteration for the `data.md` because there were so many documents, and a second iteration for `architecture.md`, `user-interface.md` and `user-stories.md` to bring the project into a state that is not overengineered, on the principle of starting small with the first variation; the implementation plan followed and its milestones were carried out one after another, the first three or four of them on video. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-summary-iterations]] ^s39
- The results can be verified through screenshots and the browser console, tests and a way of testing the software product through would be possible as well, and clicking through the page is itself a kind of testing in which one learns about the project, the data and one's own requirements, knowledge that is played back into the knowledge documents. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-verification-summary]] ^s40
- A document summarising all information about the project counts as best practice, and the final README describes an interactive dashboard with a Dune-inspired dark theme while statements such as the asserted MIT license are hallucinated and can simply be deleted. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-readme]] ^s41

## Terms

- **Thinking Matrix**: a juxtaposition of all Markdown documents of a project, used as a thinking tool to expose their relations and inconsistencies. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-thinking-matrix]]
- **Expert Developer in the Loop**: the development-side counterpart of the expert role, needed where an interface defect has to be addressed through the technical identifier of the element. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-identifier]]
- **Informed vibe coding**: working with these systems on the basis of domain knowledge and sufficient AI coding literacy, distinguished by the speaker from vibe coding. [[10_markdown/documents/promptotyping-video-2-live-demo#^v2-ai-coding-literacy]]

## Open questions

- Exploration as a phase. The paper runs Exploration as a phase that precedes Distillation and ends when there is a documented understanding of what is feasible, and it has Distillation compress what Exploration taught. The video shows the exploration resumed inside the Implementation phase, where the speaker interrupts the aggregation run with the finding that the exploration phase was not thorough enough and orders the `data.md` updated with the new knowledge (^s26, ^s27); the same source also proposes a second exploration pass in a fresh session as a check (^s7). Both wordings stand; whether the paper's phase order describes an ideal sequence or the actual one is the question this raises.
- The expert role. The video carries two roles, the Critical Expert in the Loop who checks whether what the interface shows is actually right (^s32), and the Expert Developer in the Loop, invoked where the defect has to be addressed through the element identifier and where passing it as a hash presupposes HTML-specific knowledge (^s33). The paper carries only the Critical Expert in the Loop and names no development-side role.
- Milestone verification. The paper states that Implementation advances in milestones, each a small increment the Critical Expert verifies before the next begins. In the video the run continues to the next milestone on a bare `continue` (^s28), and the verification through screenshots and console arrives after several milestones have been built (^s31, ^s40). Whether the paper describes the rule and the video an abbreviation for the demonstration is open.
- Internal inconsistency of the source. The tool identifies 76 Excel documents in the data folder (^s3), while the journal it writes later records 77 (^s22, where the figure is carried in the block). The source does not resolve the difference, so no count is grounded here.
- The demonstration is a teaching case without a repository, and its figures describe one recorded session.
